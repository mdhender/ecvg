# AGENTS.md

This file provides guidance to coding agents when working in this repository.

## Project

`ecvg` (module `github.com/mdhender/ecvg`) is another attempt at implementing Empyrean Challenge from the 1978 rulebook.
It is at the very beginning: the root `ecvg` package (`version.go`, a `semver.Version`), the `ecgen` command in `cmd/ecgen` (the game generator), the `ec` command in `cmd/ec` (the engine), the `ecview` command in `cmd/ecview`, and internal packages.
The goal is to ship the MVP: the generator follows the original 1978 setup and does not try to build a fair, balanced world.

The commands use `peterbourgon/ff/v4`. Each loads env files for the environment named by `EC_ENV` (default `development`), then reads flags from the command line and from `EC_`-prefixed environment variables (`--seed` is `EC_SEED`).
Games live in `games/{code}` (git-ignored). `internal/game` holds the record types and reads and writes the files; all generation logic is in `cmd/ecgen`.

`ecgen create [--seed N] [--homestar-template FILE] [--empire-template FILE] games/{code}` generates a whole game in one step, into an existing folder that holds none of the game's files (all are written, or none).
Files that don't change from turn to turn go in the game's folder; the state as of a turn goes in `turns/{turn}` (`deposits.json`, `empires.json`, `colonies.json`, and `order-results.json`, which is what became of the orders given in the prior turn and is `[]` in turn 0). A new game is at turn 0, so the generator makes `turns/0`, and `game.LoadData` reads the state from the folder of the turn in `game.json`.


- `game.json` holds the master data: the code, the two seeds as 16-digit hex strings, and `turn`, the number of the current turn.
- `stellia.json` holds 100 Stellia, placed by shuffling every point with x²+y²+z² ≤ 225 except the origin and taking the first 100; they get 5, 3×4, 10×3, 30×2, and 56×1 stars, in that order.
- `stars.json` holds the 163 stars, each with the `stellium_id` of its Stellium.
  The Stellia with exactly 3 stars are home Stellia (`homestellium`), and the first star (`seq_no` 1) of each is a home star (`homestar`), so a game has 10 home stars.
- `orbits.json` holds 10 orbits per star, each with the `star_id` of its star.
- `planets.json` holds the planets, each with the `orbit_id` of its orbit, at most one per orbit.
  A home star's planets come from the home star template; its home world is the planet in orbit 3.
  The other 153 stars share 688 planets (4.5 per star, rounded down): every star gets one planet in a random orbit, then the rest go into random empty orbits.
  138 of those planets (125 per 621) are `habitable`, all in orbits 2..6, split 25:50:45:20:15; within each orbit number they are picked at random.
  A planet's `viability` is 0 if it is not habitable, otherwise 1..25 on a three-dice bell curve.
- `turns/0/deposits.json` holds the deposits, each with the `planet_id` of its planet, a `deposit_no`, and a `type` (FUEL, MTL, NMTL, or GOLD).
  A home star's deposits come from the template.
  Deposits per random planet follow 3d11 + 1 (about 16 on average): that distribution is scaled to the 688 planets and shuffled across them; the types are a 34:32:32:2 FUEL:MTL:NMTL:GOLD list shuffled across the deposits.
  Each random deposit has a `size` (the refined product left in it; it loses only what a mine refines and puts into storage) and `yield` (the percentage that scales what a mine extracts in a turn), each the sum of three dice spanning its range: size 1,000,000..20,000,000 for GOLD and 1,000,000..99,000,000 for the others; yield 1..12 GOLD, 1..22 FUEL, 1..28 MTL and NMTL.
- `races.json` holds one race per home world (`id` and `homeworld_id` are both the home world's planet ID).
- `turns/0/empires.json` holds 15 empires per home world, 150 in all (`id`, `handle`, `name`, `race_id`, `homeworld_id`), all of that home world's race.
  The name is `Empire #{id}` and the `handle` (8 to 12 lowercase ASCII letters, the player) is empty until an empire is given to a player.
- `turns/0/colonies.json` holds each empire's colonies, copied from the empire template onto its home world, with `empire_id` and `planet_id`, and the default `sol`, `drt`, and `brt`.

The templates are embedded from `cmd/ecgen/homestar-template.json` and `cmd/ecgen/empire-template.json`; the two template flags name a file to use instead. Loading either rejects unknown members and invalid values.
The home star template has 10 `orbits`, each with its `orbit_no`, an optional `note` for the game master (ignored), and a `planet` (`homeworld`, `habitable`, `viability`, `deposits`; a missing boolean or number is false or 0) or `null` for an empty orbit.
The home world is always the planet in orbit 3, marked `homeworld`, habitable with viability 25; no other planet may be marked.
The default is an Earth-like system with a planet in all 10 orbits (orbit 5 is an asteroid belt) and 84 deposits.
The empire template has `colonies`, each with `no`, `type` (an entity type: `CSHP`, `COPN`, `CENC`, or `CORB`), `tech_level`, `population` (`uem`, `usk`, `pro`, `sld`), `operational` and `cargo` units (`type`, optional `tech_level`, `qty`), and optional `farming_groups` and `factory_groups` (`no` and `units`, each `qty` and `tech_level`). Its default numbers come from the sample turn 1 report in the 1978 manual.
The default keeps everything it may in the depot (FUEL, MTL, NMTL, and the stowed FACT and MINE units; AUTO, FARM, and SDRV assembled), which leaves the population, the LFSU, the FOOD, and the CNGD in the colony, under 100,000 STRS. Empires start with no mining groups, so a template can't list any (`mining_groups` is rejected), and the default has no factory groups either: those units are in cargo, and empires must assemble the groups, claiming deposits for themselves.

Record IDs of every kind run from 1 with no gaps. JSON uses `encoding/json/v2`.
`ecview --store games/{code} stellia` reads a game and writes a self-contained HTML page (from `internal/view`, no network assets) with a rotatable 3D map and a table of the Stellia (home Stellia glow and are always labelled on the map, and are starred in a sortable Home column), to a temporary file or `--output`, then opens it in the default browser unless `--no-open` is given; `--store` is also `EC_STORE`.
`ecview --store games/{code} empires` does the same for a page listing the empires for the game master (ID, name, handle, race, home world and its location, population), which can be searched, filtered by race, and sorted; selecting an empire shows its colonies: population (units, people, and the FOOD, mass, space, and life support it takes), operational units, cargo, and farming, mining, factory, and laboratory groups.

The plan:

- **Engine:** a Go command line tool to run a turn and generate reports for a game made by the generator.

## Commands

Go is 1.27 (`go.mod` says `go 1.27.4`).

```sh
go build ./...
go test ./...
go test ./internal/dotenv -run TestLoadPrecedence   # a single test
go vet ./...
go run ./cmd/ecgen create games/{code}          # the folder must already exist
go run ./cmd/ecgen create --homestar-template h.json --empire-template e.json games/{code}
go run ./cmd/ec turn report games/{code}            # write the current turn's reports
go run ./cmd/ec turn run games/{code}               # process the current turn
go run ./cmd/ec turn show games/{code}              # current turn and turn folders
go run ./cmd/ec turn rollback --confirm games/{code}   # undo the last run
go run ./cmd/ecview --store games/{code} stellia   # map of the Stellia in the browser
go run ./cmd/ecview --store games/{code} empires   # the empires and their colonies
```

## Code conventions

- Every Go file starts with the copyright and license header:
  ```go
  // Copyright (c) 2026 Michael D Henderson.
  // SPDX-License-Identifier: AGPL-3.0-or-later
  ```
- Sentinel errors are untyped constants of `cerrs.Error` (`internal/cerrs`), e.g. `const ErrX = cerrs.Error("x")`, and are matched with `errors.Is`.
- Tests are black-box (`package foo_test`) and table-driven with `t.Run`. Tests of a command (`package main`) are in the package, since a command can't be imported.
- `internal/dotenv` loads environment files for one of the environments `development`, `test`, `production`, or `agent`.
  `agent` is reserved for the coding agent's local work: use it when you need an environment.
  Precedence, highest first: real process environment, `.env.{env}.local`, `.env.local`, `.env.{env}`, `.env`.
  `.env.local` is loaded in `test` too, which is deliberately incompatible with bkeepers/dotenv.
  `*.local` env files hold secrets and are git-ignored; `.env` and `.env.{env}` are shared and never hold secrets.

## Data model (planned)

All coordinates are integers. Each level extends its parent's coordinates, and fields that don't apply are zero.

| Thing    | Coordinates                                          | Count                                 |
| -------- | ---------------------------------------------------- | ------------------------------------- |
| Stellium | `(x, y, z)`                                          | 100 per game, within 15 units of the origin, never at `(0,0,0)` |
| Star     | `(x, y, z, seq_no)`                                  | 1..5 per Stellium                     |
| Planet   | `(x, y, z, seq_no, orbit_no)`                        | 1..10 per Star                        |
| Entity   | `(x, y, z, seq_no, orbit_no, ox, oy, oz)`            | ship or colony                        |

The plural of Stellium is Stellia.
A ship orbiting a Stellium is `(x, y, z, 0, 0, 0, 0, 0)`; one orbiting a Star is `(x, y, z, seq_no, 0, 0, 0, 0)`; an open-air colony is `(x, y, z, seq_no, orbit_no, 0, 0, 0)`.
`ox, oy, oz` are small positive integers giving a position relative to the planet.

- **Planet:** habitability (bool; false forbids open-air colonies), viability (0..25, caps the planet's FARM-1 units), 1..31 deposits, each of type GOLD, FUEL, MTL (metallics), or NMTL (non-metallics).
- **Entity:** one of four types: CSHP (ship), COPN (open-air surface colony), CENC (enclosed surface colony), or CORB (enclosed orbital colony). It holds Population and Inventory units, both transferable between entities. All but COPN are enclosed. Every entity has an SOL (standard of living, default 1.0), a DRT (death rate, default 0.625%), and a BRT (birth rate, default 0.625%); the rates are stored as fractions (`"drt": 0.00625`). Every entity also has rations, an integer percentage from 1 to 500 (default 100, `"rations": 100`), which only the set rations order changes. An entity's ID is its colony's `id`.
- **Population:** four types of unit: UEM (unemployables), USK (unskilled workers), PRO (professionals), and SLD (soldiers). A unit is a block of 100 people with a mass of 1 MU; it requires 1 VU of enclosure in every type of entity (`Population.Volume`), and on a ship or in an enclosed colony it also takes 1 LU (life support unit). The population of an open-air colony wants to be enclosed but doesn't have to be: those forced to live outside will have a lower standard of living and tend to rebel (manual F3.2), which isn't built yet. A unit on a full (100%) ration eats 0.25 FOOD per turn; an entity's population eats units x 0.25 x rations, rounded up to a whole FOOD (`Population.FoodWanted`). FOOD has a mass of 6 MU and takes 3 VU to store in any entity. Population quantities everywhere, including the empire template, are units, not people.
- **Running a turn:** `ec turn run games/{code}` loads the state as of the current turn N from `turns/N`, runs the phases (`engine.RunTurn`), writes the new state to a new `turns/N+1` (built under a temporary name and renamed), and then replaces `game.json` to make N+1 the current turn. `turns/N` is never changed, and it is an error if `turns/N+1` already exists. The first phase carries out the orders in `turns/N/orders`.
- **Group numbers:** an entity's farming, mining, factory, and laboratory groups share one run of group numbers (`Colony.NextGroupNo`, `last_group_no`). A new group always gets a higher number than any the entity has given out, and a number is never reused. The senior group is the one with the lowest number. Resource allocation still goes farms, then mines, then factories, then laboratories, and by seniority within each kind. The empire template's group numbers must be unique in a colony.
- **Cadres** (`internal/game/cadres.go`): `Colony.Cadres` (`cadres`: `cwrk`, `trne`, `spy`) counts the cadres drafted in an entity. A cadre is made up of population units that stay in the population record, so they still eat and take space, but they are allocated by the empire and so are out of the worker (WRKR) cadre (`Colony.FreePRO`, `FreeUSK`, `FreeSLD`). SLD is not a cadre: a drafted SLD is a USK that becomes an SLD, 1 for 1. CWRK is 1 PRO and 1 USK each. TRNE is 1 USK each plus 1 PRO for every 100 TRNE in the cadre or part of that (the total is rounded up, so 1 TRNE needs a whole PRO); TRNE is greedy and usually limited by PRO. SPY is 1 PRO and 1 SLD each. Each CWRK does 500 EMU of assembly work a turn (see Assembly). If the population shrinks (starvation, SLD becoming PRO), the Demographics phase cuts the cadres to fit (`Cadres.Fit`): SPY keep their people first, then CWRK, then TRNE; that order is our choice, not a rule from the designer. Cadres are not population units: the report lists them in their own CADRES section, and the POPULATION section shows the actual population units. CWRK and SPY stay until the empire disbands them. WRKR and TRNE disband by themselves. The draft comes before production (manual B3.0), so a TRNE cadre trains in the turn it is drafted in: its people are out of the worker cadre for that turn's production, and in the Demographics phase 5% of the trainees, rounded down, turn from USK into PRO and the cadre is disbanded, freeing the rest (`Colony.Train`, the colony's `trained`). Nobody is promoted in the setup turn, so trainees drafted then train in turn 1. The empire template may give a colony `cadres`, an object (`{"cwrk": 1000}`; `cwrk`, `trne`, `spy`), which its population must be able to make up; the default starts with 1,000 CWRK.
- **Orders:** players return one plain text file per empire, `turns/N/orders/empire-{id}.txt` (the same name as the empire's report; leading zeros are optional). `internal/orders` reads them: `Lex` splits a line into tokens, `Parse` turns a file into orders, and `LoadTurn` reads a turn's folder. One order per line, and an order can't span lines. Keywords ignore case; text is UTF-8; any run of white space separates tokens; text in double quotes is one token. A token that starts with `#` or `//` starts a comment that runs to the end of the line, but not inside quoted text and not when joined to the end of a token (`set rations#` is two tokens, `set` and `rations#`). Blank lines are ignored. `engine.ApplyOrders` carries the orders out in empire ID order, then line order. An order that doesn't parse, or that its empire may not give, is rejected: `ec turn run` prints `rejected file:line: text: reason` and the turn still runs. A file in the orders folder that isn't named for an empire in the game (other than dotfiles) fails the run before anything changes. Every order, accepted or rejected, is recorded in `turns/N+1/order-results.json` (`game.OrderResult`: `empire_id`, `line`, `text`, `accepted`, and `reason` if rejected), and each empire's report for turn N+1 lists its own under "ORDERS RECEIVED FOR TURN N".
- **To do, the manual's orders:** `docs/rules/manual.md` is being rewritten to the order syntax the engine accepts. Done: S2.0 (general rules), S6.0 (assemble, disassemble, scrap, and the group orders), S8.1, S8.5, and S8.6 (update factory group, shut down, restart), and S12.1, S12.2, and S12.4 (draft, disband, set rations); the table at the top of chapter S says which rules are rewritten. Still in the 1980 syntax: every order the engine doesn't take yet. For those the manual is not the authority on order formats.
- **The orders so far:**
  - The update group orders (`orders.UpdateGroup`, `engine.UpdateGroup`; manual S8.1, S8.5, and S8.6, which are up to date): `update GroupKind-group GroupNo of EntityID shutdown (Quantity | PercentageAmount)` and the same with `restart`, for a `farming`, `mining`, `factory`, or `laboratory` group; and, for a factory group only, `update factory-group GroupNo of EntityID retool` and `update factory-group GroupNo of EntityID produce Unit`. They replace the 1980 BCH order and the SHT and STU orders (and the shut down and start up forms of MCH); there is no `set idle` order any more. Shutdown and restart change the group's `shut_down`, the number of its units shut down by order: a quantity, or a percentage (`1%` to `100%`) of all the group's units, rounded up for a shutdown and down for a restart, and capped at the units running or shut down (the order is rejected only if there are none). Units shut down (`game.ShutDownUnits` shares the count among the entries of the group's units, in the order listed) ask for no staff or fuel, so the order is how an empire saves FUEL; units assembled into the group later are running. Retool clears the group's `producing` and sets `retooled`; produce sets `producing` and clears `retooled`, and is rejected unless the group has retooled or it changes from one structural unit (`STRN`, `STRL`, `STRS`) to another (manual H3.6). The retooling itself (it waits for work in process and costs 0.01 MTL and 0.01 NMTL per FACT) comes with manufacturing. Factories don't make `RSCH` (laboratories do), so an order to produce it is rejected.
  - `draft Quantity UnitOrCadre from EntityID` and `disband Quantity UnitOrCadre from EntityID`: see manual S12.1 and S12.2, which are up to date (`engine.Draft`, `game.Colony.Draft`, `game.Colony.Disband`).
  - The group assemble orders (`orders.AssembleGroup`, `engine.AssembleGroup`): `assemble factory-group on EntityID with Quantity FACT-n [producing Unit]`; `assemble farming-group on EntityID with Quantity FARM-n`; `assemble mining-group on EntityID with Quantity MINE-n working DepositNo`; `assemble laboratory-group on EntityID with Quantity LAB-n`; and, to add to a group, `assemble factory-group GroupNo on EntityID add Quantity FACT-n`, `assemble mining-group GroupNo on EntityID add Quantity MINE-n`. The farming and laboratory orders have no form with a group number: their units join the entity's group of that kind and of their tech level, or start it. A unit with a tech level is written CODE-TL (`FACT-10`); one without is its code (`CNGD`). An order takes units of one tech level, the group's (manual H3.0). A new factory group must have a producing unit; it must be one factories make (`units.Def.FactoryMade`: a manufactured unit, so not `RSCH`); it is recorded on the group (`producing`) and nothing uses it yet. The empire template's `factory_groups` must each have `producing` too (`{"type": "FARM", "tech_level": 1}`, no `qty`; never `RSCH`). DepositNo is the deposit's number on the entity's planet, as the report shows it. In the orders phase the order is checked, the new group is made at once (`Colony.NextGroupNo`; a new mining group claims its deposit then), and assembly work is started for each unit entry; see Assembly below. It is rejected, changing nothing, if the group to add to doesn't exist, a group would mix tech levels, the entity has none of the units in storage (cargo plus depot) free of other assembly work (if it has some, but fewer than the order asks for, the order takes the ones it has), the entity can't have such a group (`game.CanInstallFarm`, `game.CanAssembleMines`), the planet's FARM-1 cap (everyone's units, assembled or being assembled) would be passed, or the deposit isn't on the planet or is worked by any empire's mining group (first come, first served).
  - `assemble Quantity Unit on EntityID` (`assemble 5,000 HDRV-1 on 15`), `disassemble Quantity Unit on EntityID`, and `scrap Quantity Unit on EntityID` (`orders.UnitWork`, `engine.UnitWork`) have the entity's CWRK assemble units that are in its storage (never people: cadres are drafted, and `assemble 5,000 CWRK on 5` is rejected with a pointer to `draft`), take assembled units back down into storage (the order is spelled "disassemble" for historical reasons), or scrap units for 70% of their MTL and NMTL. The orders phase checks the order and starts the work; see Assembly. Assembling or disassembling a unit that is never assembled (`units.Def.RequiresAssembly`) is valid and does nothing, without a word in the report (brutal mode). Scrap only ever takes units in storage (cargo and depot), never assembled ones, so `scrap 100 HDRV-1 on 15` can't scrap the engines that move the ship. Rejected: FACT, FARM, LAB, and MINE to assemble or disassemble (`engine.ErrGroupUnit`; the group orders assemble them and nothing disassembles a group yet); a unit that wasn't built from MTL and NMTL, or PRTO, to scrap (`engine.ErrNotScrappable`); an entity with none of the units in storage free of other assemble and scrap work (`engine.ErrNotEnoughUnits`), or none assembled free of other disassembly work (`engine.ErrNotEnoughAssembled`). An order for more units than there are works on the ones there are, as a draft does.
  - `using Quantity CWRK` may end any of the unit orders and the group assemble orders (`assemble 5,000 HDRV-1 on 15 using 20 CWRK`): it caps the CWRK that work on the order in a turn (`MaxCWRK`). `CWKR` is read as `CWRK` there, since both spellings turn up.
  - `set rations for EntityID to PercentageAmount` sets the entity's rations. EntityID is the ID of an entity the empire controls. PercentageAmount is a whole number from 25 to 100 (manual G4.1) with the `%` joined to it: `50%`, not `50 %`. When an entity gets several, the last one wins.
- **Turn folders:** `turns/N` holds everything about turn N: the state as of its start (which is the result of turn N-1), `reports/`, the reports made from that state and sent to players, and `orders/`, the orders the players return for turn N. So state(N) + orders(N) -> state(N+1), then reports(N+1). Turn 0 holds the setup state.
- **Reports:** `ec turn report games/{code}` writes a plain text report per empire as of the current turn to `turns/N/reports/empire-{id}.txt` (`internal/report`), replacing any already there: the empire, what became of the orders it gave in the prior turn (not in turn 0), each colony (entity ID, rations, population, units, cargo, groups), and the home world's deposits.
- **Show and rollback:** `ec turn show games/{code}` prints the current turn and each turn folder's report and order counts. `ec turn rollback --confirm games/{code}` undoes the last run (without `--confirm` it only says what it would delete, and fails): it makes N-1 current in `game.json` and deletes `turns/N` (state, reports, and orders); it fails at turn 0.
- **Turns:** the first turn of a game is turn 0, the players' setup turn, in which demographic changes don't apply. A year is 4 turns, and a turn whose number is greater than 0 and divides by 4 is an end-of-year turn. A turn is processed in phases, in `internal/engine`. `engine.RunTurn` runs them in the order of the manual's turn sequence (B3.0): orders (`engine.ApplyOrders`, which also runs in turn 0), then dis-assembly (B3.4), assembly (B3.8), the draft (B3.12), production (B3.17: resource allocation, farming, rations, population changes, which are the deaths by starvation, mining, and research), and demographic changes (B3.20). Every order is still checked, and its work started, in the orders phase, before any stage runs: an order is not checked at its own stage, so an empire can't assemble in a turn the units it disassembles in that turn. Dis-assembly, assembly, and the draft also run in turn 0; the rest don't happen in it.
  - **Resource allocation** (`engine.AllocateResources`): makes each colony's worker cadre (WRKR) for the turn (`game.NewWorkers`, `game.Workers`). The cadre is per colony and is remade every turn from the idle units, the PRO, USK, and assembled AUTO that the empire's orders haven't allocated to something else (no order allocates any yet, so today that is all of them). An AUTO unit joins as the USK it stands in for, TL^2 each (`game.AutoUSK`): 1,000 AUTO-10 join as 100,000 USK. AUTO never replaces PRO, which is the tightest constraint on an empire's expansion. The cadre is virtual: population records don't change. Moving workers costs nothing because it only ever happens in this phase. CWRK is a different cadre: its PRO and USK are allocated by the empire, so they will not be in the worker cadre. The colony's `workers` records the cadre (`pro`, `usk`, `auto_usk`) and what nothing used (`idle_pro`, `idle_usk`), and the next report shows it under WORKERS LAST TURN. In the full phase order this comes after combat; orders that allocate resources will have priority over the cadre. The phase then shares the cadre and the colony's FUEL among the groups and returns an `engine.Allocation` per colony, which production carries out. The scheme is deliberately blunt ("brutal mode"), not efficient: don't optimise it. It makes two passes, each over farming groups, then mining groups, then factory groups (factory groups aren't allocated to yet), then laboratory groups, and each kind in order of seniority, which is the group number, lowest first. There are two levels of idle, and the phase respects the first and sets the second: units idled by the empire's order ask for nothing, and units that asked and got no staff, or staff but no fuel, are idle from shortage. Both are recorded on the group's units (`idle`: `ordered`, `unstaffed`, `unfuelled`; rewritten every turn), production respects them, and the report shows them under the group, along with the group's standing `shut_down`. (1) Staff: each group takes as much of the cadre as it can use, until the cadre runs out; staff is never given back, even by a unit that then gets no fuel. (2) FUEL: each group takes as much as its staffed units can use, and the pass stops when the fuel runs out or at the first group that asked for staff and got none (a group that is wholly idle by order is passed over).
  - **Farming** (`engine.Farming`): the FARM units in each colony's farming groups make FOOD, which goes into the colony's cargo before the rations are eaten. In each turn it works, a FARM-1 makes 25 FOOD and a FARM-2 to FARM-10 makes 5 x TL (`game.FarmFood`; manual H1.1). A unit works only if resource allocation gave it staff and fuel. Staff is 1 PRO and 3 USK from the colony's worker cadre. Food is the priority when resources are allocated: farms get staff and FUEL before anything else does. Fuel is 0.5 x TL a turn for FARM-1 to FARM-5 and 1 x TL for FARM-6 to FARM-10, the total rounded up (`game.FarmFuel`), burned from the FUEL in cargo; FARM-2 to FARM-5 in an orbital colony in orbits 1..5 are solar powered and burn none (`game.FarmSolar`). Units are taken in group order, then the order listed, so when staff or fuel runs short the later units sit idle. What happened is recorded in the colony's `harvest` (`units`, `worked`, `ordered`, `unstaffed`, `unfuelled`, `fuel`, `food`, `lost`; omitted when the colony has no farms) and shown in the next report under FARMING GROUPS. POWR as a substitute for FUEL is not implemented.
  - **Dis-assembly and assembly** (`engine.Disassembly`, `engine.Assembly`, `game.Colony.Disassemble`, `game.Colony.Assemble`, `internal/game/assembly.go`): two phases that run before the draft and before production, as in the manual's turn sequence (B3.4 and B3.8), in the setup turn too. Dis-assembly, which does the disassemble and scrap work, comes first, as in the rulebook, so that what it returns to storage is there for the phases between the two (transfers, when they exist) and an empire can't double dip; the two share the turn's CWRK pool, so dis-assembly has first call on it whatever the age of the work, and assembly gets what is left. A colony's CWRK make a pool of 500 EMU (equivalent mass units) each (`game.EMUPerCWRK`); CWRK drafted this turn aren't in it yet. Each piece of work (`Colony.Assembly`, `assembly` in the JSON: `action`, which is omitted for assemble and otherwise `disassemble` or `scrap`; `kind` and `group_no` if the units join a group; `unit` still to do; `emu` done; `max_cwrk` for a cap), oldest first, takes as much of the pool as it can use; unused EMU is lost. The allocator swarms: by default work takes everything it needs to finish in one turn, and it does not try to be efficient. An order's `using Quantity CWRK` caps what its work takes in a turn at 500 EMU per CWRK (`max_cwrk`); a cap above what the work needs changes nothing. A unit is done when the work reaches its mass (`units.Def.Mass`, the total rounded up), so partly done units keep their EMU between turns. Scrap takes more: a CWRK scraps only 300 MU a turn (`game.ScrapMUPerCWRK`, manual F11.0), so a MU of scrap takes 5/3 EMU, the total rounded up. Assembled units move from storage (cargo first, then depot) into use and join their group if they have one: into `depot_operational` if the colony has a depot and the unit may be there (`units.Def.DepotAllowed`; so an open-air colony's groups take none of its space), otherwise into `operational`. Structure always goes into `operational`: in the depot it would enclose nothing. Disassembled units go the other way: from `depot_operational` into `depot`, and from `operational` into `cargo`; it takes the same EMU as assembling, and 10% of the units an order disassembles are lost (`game.DisassemblyLossPercent`, manual F10.3): the loss is 10% of the order's units so far, rounded down but at least 1 unit, so an order for a single unit loses it (the work's `done` counts them and `destroyed` is last turn's loss), so it is the same however many turns the work takes. Either way the units move only if the entity is within its capacity afterwards or no further over it than before (`Colony.fit`, manual F3.2.2 and F3.2.4; the work waits, `waiting: "room"`): most units require twice the enclosure assembled, and structure makes space only when assembled and takes it only when stowed. So assembling structure and disassembling anything else are never limited, since they only free space; assembling anything else needs room, and structure that is holding the cargo can't be taken down. Scrapped units leave storage and 70% (`game.ScrapPercent`, manual F11.0) of the MTL and NMTL that built them, each total rounded down, is stored like mined resources (`Colony.StoreResource`); what a ship or orbital colony has no room for is lost (the work's `mtl`, `nmtl`, `lost`); an enclosed surface colony keeps them in its external depot. Because assembly comes before production, a unit assembled in turn N works in turn N. The colony's `construction` (`pool`, `used`) and each work's `assembled` feed the report's ASSEMBLY section; finished work is dropped a turn later. Not built: disassembling units that are in a group (FACT, FARM, MINE), anything that reacts to assembled units other than AUTO and structure, and factory production.
  - **Mining** (`engine.Mining`): Every mining group is assigned to one deposit, and a deposit is worked by at most one mining group. Each MINE unit that resource allocation gave staff (1 PRO and 3 USK) and FUEL (0.5 x TL a turn, the total rounded up, `game.MineFuel`) extracts 25 x TL x the deposit's yield percentage of refined product, the group's total rounded down (`game.MineOutput`): GOLD, FUEL, MTL, or NMTL, as the deposit is. The product goes into the colony's depot (an open-air colony) or cargo (an enclosed surface colony), and the same amount comes out of the deposit's `size`; a deposit can't give more than it has left. A group whose deposit is exhausted still takes its staff and burns its fuel, and mines nothing: the empire has to idle it (this is intended). Each group's `mined` (`worked`, `fuel`, `product`, `returned`) records the turn and the next report shows it. If an enclosed colony's cargo has no room for GOLD or FUEL, the excess is returned to the deposit (see Capacity); its MTL and NMTL are kept in its external depot and never run short of room (manual H2.2). Mining groups can only be assembled by surface colonies, open-air or enclosed, never by orbital colonies or ships (`game.CanAssembleMines`); the mining-group assemble order makes them.
  - **Tech levels** (`orders.AssembleTechLevel`, `engine.AssembleTechLevel`, `Colony.StartTechLevel` in `internal/game/techlevel.go`; manual S6.7, J4.1, J4.2): `assemble tech-level on EntityID [to TL-n] [with Quantity PRTO-n] [using Quantity CWRK]`. No `to` means one level up. Every level is paid for when the order is accepted, all or nothing (`game.ErrNotEnoughResearch`): with RSCH (`game.TechLevelCost`), or, only if the order has a `with` clause, with PRTO-n units, which hold `game.PrototypeResearch` points and are used up whole, as few as pay; the remainder becomes RSCH if the colony has assembled laboratories and is lost otherwise. The job is a `game.Assembly` with `Action: game.WorkTechLevel`, whose `Unit.TechLevel` is the target and whose `Need` is the EMU it takes: the colony's capacity (enclosed VU, rounded up) times the levels gained, fixed when the order is accepted. `Colony.Assemble` does it in queue order with the other assembly work, and sets `Colony.TechLevel` when it is all done; there is no benefit before that. An order that would not raise the level (`game.ErrTechLevelNotHigher`), goes past TL 10 (`game.ErrTechLevelTooHigh`), or comes while a job is in progress (`game.ErrTechLevelInProgress`) is rejected.
  - **Prototypes and transfers** (`internal/game/transport.go`, `internal/engine/transfer.go`; manual S6.9, S7.1, J4.2, K2.1): `assemble PRTO-n on EntityID from laboratory-group GroupNo` (`orders.AssemblePrototype`, `Colony.MakePrototype`) turns `game.PrototypeResearch(n)` RSCH into one PRTO-n at once; the group must have assembled LAB-n units (`game.ErrNoLabGroup`, `game.ErrPrototypeTechLevel`), running or not, and the prototype goes into cargo whatever the room. `transfer Quantity Unit from EntityID to EntityID` (`orders.Transfer`, `engine.Transfer`, `Colony.Transfer`) is carried out in the orders phase, in order, so what arrives can be used by later orders. `ApplyOrders` starts each colony's `Transport` (`transport` in the JSON) for the turn: its fleet is every TRNS it has, stored or in use (TRNS are never assembled), with 200 x TL^2 MU each. A transfer's mass is rounded up to a whole MU; FUEL is the turn's MU / 2,000 rounded up (`game.TransportMUPerFuel`), and the crew is one PRO per 10 TRNS used, highest tech level first, limited by `FreePRO` and taken out of the turn's worker cadre (`game.NewWorkers`). The order takes what there is: the unclaimed units in storage, what the TRNS can carry, and the whole units the receiver has room for (its depot, if the unit may be there, is unlimited). TRNS move themselves, and the fleet is fixed at the start of the phase, so the sender keeps their use and the receiver gets it next turn. Rejected: RSCH itself (`engine.ErrResearchNeedsPrototype`), another planet (`engine.ErrNotSameOrbit`), another empire's entity (`engine.ErrForeignTransfer`; REC orders aren't built), and, in the parser, people and entity 0 (jettison). Not built: pick-ups, the multiple transfer order, and a record on the receiving side.
  - **Research** (`engine.Research`, `internal/game/labs.go`): laboratories replace the 1980 rule that factories build research. LAB units are assembled into laboratory groups (`Colony.LaboratoryGroups`, `laboratory_groups`; `game.KindLaboratory`), which work like farming groups: every unit of a group is of one tech level, and an entity has at most one laboratory group of each tech level, so the assemble order takes no group number. Any colony may have them, but a ship can't (`game.CanAssembleLabs`, `game.ErrLabSite`), though it may carry LAB units in storage; in an open-air colony the assembled units are in the depot. Each LAB unit that resource allocation gave staff (3 PRO and 1 USK, `game.LabPRO`, `game.LabUSK`; AUTO stands in for the USK) and FUEL (0.5 x TL a turn, the total rounded up, `game.LabFuel`) makes 0.25 x TL of a research point. The quarters of all the colony's laboratories are added up and the total is rounded down (`game.LabQuarters`, `game.LabResearch`); the fraction is lost, not carried over. The RSCH goes into the colony's cargo as an `RSCH` unit (`Colony.AddResearch`); it has no mass or volume, so there is always room, even in an entity that is over its capacity. Laboratories are the last to be allocated staff and FUEL, after the factories, so research gets what production leaves; that is our choice, not a rule from the designer. The colony's `research` (`units`, `worked`, `ordered`, `unstaffed`, `unfuelled`, `fuel`, `rsch`; omitted when the colony has no laboratories) records the turn, and the next report shows it under LABORATORY GROUPS. No research is done in the setup turn. Not built: a way for an empire to get LAB units, since factories don't produce yet; the default empire template has none, and its groups can't include laboratory groups, so a template has to list LAB units in cargo or the depot for an empire to assemble.
  - **Rations** (`engine.Rations`): each entity's population eats its FOOD from the entity's cargo. If the cargo holds less than the rations call for, it eats all there is (`engine.Feed`).
  - **Population changes** (`engine.PopulationChanges`; the phase can raise or lower population): so far only starvation. The ration R an entity got is always worked out from the FOOD it actually ate, 400 x eaten / units percent, never from the rations it was set to. If R is less than 25%, max(1, 100-4R) percent of its units starve to death, rounded up to a whole unit; 20% starve at R = 20, 80% at R = 5, everyone with no food. The deaths are shared among the unit types in proportion to their numbers, rounded down, and the deaths left over are taken first from UEM, then SLD, then USK, then PRO (`Meal.Starved`). The loss is recorded in the colony's `starved` (omitted when nobody starved) and shown in the next report. Births and deaths from BRT and DRT are not implemented.
  - **Standard of living (not yet computed):** the ration percentage will be one of its inputs.
  - **Demographic changes** (`engine.Demographics`): (1) if UEM is strictly more than 30% of an entity's population, 2% of UEM (rounded up) become USK; then (2) if the prior turn was an end-of-year turn (prior turn > 0 and divides by 4, so this happens in turns 5, 9, 13, ...), 5% of SLD (rounded up) become PRO.
- **Units:** manufactured or processed items with mass (MU) and volume (VU). Volume has assembled and unassembled values; most units are bigger assembled.
- **Unit catalogue:** `internal/units` holds a `Def` for each of the 43 unit codes in `unit-tables.md` (`units.Lookup(code)`, `units.All()`): name, class, whether it carries a tech level (1..10, otherwise 0), whether it needs assembly, and whether it is manufactured. `LotSize(tl)` is the units one build adds; `Inputs(tl, lots)` is the MTL and NMTL for whole lots (not ok for units that aren't manufactured, and for PRTO, whose inputs aren't settled); `Mass`, `Volume`, and `StowedVolume(tl, qty)` are totals for a quantity, as an exact fraction (`units.Frac`: `Add`, `Sub`, `Mul`, `Div`, `Cmp`, `Sign`, `Ceil`, `Floor`). The engine keeps the fractions and never rounds them; only a report rounds, up, when it shows a figure, so a report's totals needn't add up. Lots are only how units are built: a per-lot number in the tables is divided by the lot size, exactly. `Encloses()` is the STRN equivalents an assembled structural unit provides. Living and Cadre codes are in the catalogue as people (1 MU, 1 VU, `Def.Population()`), and RSCH has no mass or volume. The tests read `unit-tables.md` and check the catalogue against every row, so change the two together. The empire template's units must be in the catalogue (not population or RSCH) with a valid tech level, and its operational units must be of a kind that is assembled. The catalogue doesn't yet hold what a unit needs to operate (labour, fuel) or what it produces.
- **GOLD:** a resource used in trading only. It is stored like MTL (1 MU, 0.5 VU).
- **Salvage:** the home colony's FARM-10, LFSU-10, and SDRV-10 units were scavenged from the generation ship. A TL-1 colony's factories build only TL-1 units, so they are irreplaceable. Its 100,000 STRS were salvaged too: structure has no tech level, but a TL-1 surface colony builds only STRN (manual H3.8), so it can't make more of them.
- **Where farms go** (`game.CanInstallFarm`; nothing installs farms yet, since there are no assembly orders):
  - FARM-1: only by an open-air surface colony, on a planet that is habitable with viability > 0, in orbits 1..5. Installed FARM-1 units are not stored in the colony; they are in the "depot" bucket, outside the entity. A planet holds at most viability x 100,000 FARM-1 units (`Planet.FarmCap`), which is the total for all the empires on it, not a limit per empire. Only FARM-1 units count against it: they are the farmsteads on arable land.
  - FARM-2 to FARM-5: an orbital colony in any orbit, or a surface colony (open-air or enclosed) in orbits 1..5, habitable or not. Not ships.
  - FARM-6 to FARM-10: a ship or any colony, in any orbit.
- **Structure** (manual F3.0, H3.8): the structural units are STRN (structure), STRL (light), and STRS (super-light); the manual's STUN, STUL, and STUS were renamed to these. None carries a tech level. Each is 0.1 MU, requires 0.05 VU stowed and none assembled, and is built in lots of 100 (from 7 MTL and 3 NMTL, 5 and 5, or 2 and 8). Assembled, a STRN counts as 1 STRN equivalent, a STRL as 5, and a STRS as 20 (`units.Def.Encloses`). All three absorb damage at the same rate. Not built: which entity builds which (STRN only in surface colonies; orbital colonies build STRL at TL 1-4 and STRS at TL 5-10).
- **Capacity** (`internal/game/capacity.go`, manual F3.0): every entity has a capacity, in VU, and it is only about volume (engines worry about mass, and life support about population). Capacity is the STRN equivalents of the entity's assembled, operational structure (`Colony.StructureEquivalents`) divided by its structure ratio (`EntityType.StructureRatio`: open-air colony 1, enclosed surface colony 5, orbital colony 8, ship 10), exactly (`Colony.Capacity`). Everything in the entity counts against it (`Colony.SpaceUsed`): population, in an open-air colony too, operational units at their assembled volume, and cargo at its stowed volume, all exact fractions. Assembled structural units take no space; structure stowed in cargo does. Capacity is checked every time something is stored (`Colony.Room`, `Colony.StoreCargo`): an enclosed entity (every type but the open-air surface colony) accepts only the whole units that fit, an exact fit included (manual F3.2.1), and it is up to the empire to shift things around. An open-air surface colony may hold more than it encloses (manual F3.2), so it always has room, and assembly and disassembly never wait for room there; the manual's dispossessed population and rebels aren't built. So FOOD an enclosed colony has no room for is lost (the harvest's `lost`), and mined GOLD or FUEL an enclosed colony has no room for is returned to the deposit (the group's `returned`): the empire pays to extract it and gains nothing, and the deposit loses nothing. An entity may hold more than its capacity (a template can start that way, and nothing is thrown out); it just can't store more. The report shows capacity, used, and free or over under SPACE, each rounded up, and the population's `Space wanted` for an open-air colony. Assembling structure raises capacity and disassembling it lowers it; disassembling structure waits rather than push the entity over its capacity.
- **Depots:** an open-air surface colony, and only that type, has a depot (`Colony.HasDepot`): a bucket outside the entity, unlimited, whose contents take none of the colony's space. `depot` lists the units stored there and `depot_operational` the units assembled and in use there. Weaponry, Commodity (FOOD, CNGD), Static (LFSU), and Technology units must be in the entity, in cargo or operational; an open-air colony can keep everything else in its depot (`units.Def.DepotAllowed`). Mined resources go to the depot (`Colony.StoreResource`). An enclosed surface colony has no depot, but it keeps the MTL and NMTL it mines or recovers from scrap in an external depot (manual H2.2): they go in its `depot` list, which holds nothing else, take none of its space, and the report lists them under EXTERNAL DEPOT. FUEL is spent from the cargo first and then the depot (`Colony.Stock`, `Colony.Spend`). AUTO units count toward the worker cadre from either operational list. The empire template may list `depot` and `depot_operational` for a COPN colony, and rejects units there of a class that isn't allowed. Planned: installed FARM-1 units live there, and mining and factory groups can be assembled there. Rations are eaten from cargo only.
- **Groups and tech levels:** every unit of a group is of the same tech level, whether it is a farming, mining, or factory group (manual H3.0 for factories), so a group's `units` have one entry. The empire template enforces it for farming and factory groups, and `engine.AssembleGroup` rejects units of another tech level with `ErrTechLevel`.
- **Group limits:** an entity has at most one farming group of each tech level (manual H1.0), so the farming order takes no group number: the units join the entity's group of their tech level, and a new group is made if it has none; at most 25 factory groups (`game.MaxFactoryGroups`, manual H3.0; `ErrTooManyGroups`), and one mining group for each deposit, which no other mining group of any entity may work (`ErrDepositClaimed`); the manual's limit of 40 mine groups is dropped. The empire template checks the first two.
- **Shared limits are first-come, first-served:** orders run in empire ID order, so a limit shared by the empires on a planet (the FARM-1 cap) goes to whoever's order is carried out first. This is intended.
- **Production:** farming makes FOOD; mining extracts deposits into GOLD, FUEL, MTL, NMTL; manufacturing turns resource units into manufactured units (CNGD, SDRV, ...).
